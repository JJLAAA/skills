# 同步文档目录索引与摘要

## 目标

让文档目录始终保持：
1. 每个文档开头有准确、可扫描、可机器解析的 `> **文档摘要**` 块，帮助人类和 Agent 在 30 秒内判断"这篇是否该读、解决什么任务、有哪些核心结论、依赖哪些文档"
2. 根目录有一份完整的 `README.md` 索引，包含文档地图、任务入口、概念索引、交叉引用、推荐阅读顺序和核心结论速查
3. 各文档的章节标题清晰、具体，不使用模糊泛化的标题

另支持**单篇文章整理**：将文章开头的"修订"章节中的补充思考，融合到正文的合适位置。

### 索引设计原则

- **先判断，再阅读**：摘要和 README 必须让读者快速判断是否需要打开全文，而不是只复述文章内容
- **任务优先**：除主题和概念外，必须提取"这篇文档能帮助完成什么任务"，因为人类和 Agent 常按任务检索
- **关系类型明确**：文档关联必须使用固定关系类型，避免只写自然语言导致阅读顺序和依赖关系不清
- **结论可复用**：核心结论必须是完整观点或决策依据，不写成章节名或关键词
- **稳定结构**：摘要块和 README 表格字段尽量稳定，便于 Agent 抽取、比较和增量更新

---

## 模式判断

- 用户提到**具体的单个文件**，或说"整理这篇文章"、"把修订合并"→ 进入**单篇整理模式**（见下方）
- 用户提到**目录**、"同步"、"更新索引"→ 进入**目录同步模式**（见"目录同步执行流程"章节）

目录同步模式下，还需进一步确认**同步子模式**（必须询问用户，不得擅自决定）：

- **初始化模式**：处理目录下所有文件，不跳过任何文件
- **增量模式**：只处理**最近一周内有过修改**的文件（`mtime` 距今 ≤ 7 天），其余文件跳过

询问示例：
> 请问要用哪种同步模式？
> - **初始化模式**：扫描并处理所有文件
> - **增量模式**：只处理最近 7 天内有更新的文件
>
> （如不确定，增量模式适合日常维护，初始化模式适合首次建立索引或全量重建）

## 单篇整理模式

### 背景

用户有时会在文章开头追加一个"修订"章节，记录自己在读完/写完后的补充思考、修正或新视角。这些思考不是独立的，而是对正文某处内容的深化或纠正，应该被整合到正文的相应位置，而不是孤立地堆在开头。

### 执行步骤

**第一步：读取文件，识别修订章节**

读取用户指定的文章，寻找文章开头（正文之前）的"修订"章节。修订章节的典型特征：
- 位于文件顶部（通常在标题或摘要块之前，也可能紧跟其后）
- 标题包含"修订"、"修订记录"、"后记补充"、"Revision"等字样
- 内容是作者事后追加的想法、订正或补充观点

如果没有找到修订章节，告知用户"未发现修订章节，无需整理"，结束执行。

**特殊情况：修订内容已在正文展开**

修订条目有时不是"待插入的内容"，而是作者对已完成整合的注记（如"对 X 进行了详细解释，见 Y 章节"）。识别方式：
- 修订条目提到了正文中已存在的章节名
- 正文中该章节的内容已经覆盖了修订描述的要点

此时处理方式不同：不是插入内容，而是检查原提及处是否有指向该章节的交叉引用——如果没有，补充引用链接，然后删除修订头即可。

**第二步：分析修订内容，规划插入位置**

对每一条修订思考，判断：
1. 它针对正文哪个章节/段落？（根据主题、概念、引用关系判断）
2. 应以何种方式融合？
   - **补充**：在对应段落末尾追加为新的子段落或注记
   - **修正**：在相关论断旁边加入修正说明（保留原文，在其后用"[修订]"引导补充内容）
   - **新增小节**：如果思考足够独立且篇幅较大，在最相关的章节下新增一个小节
   - **扩展引言/结论**：如果思考是对全文视角的补充，整合到引言或结论段

向用户展示整合计划（不要直接动文件），先输出一条修订内容的概括性总结，再列出详细计划，格式如下：

```
📝 修订概要：本次修订共 N 条，主要涉及 [对修订内容的概括总结：核心主题/方向，如"对 XX 概念的深化与 YY 结论的修正"]。

修订整合计划：

1. 修订内容："[修订原文摘要]"
   → 融合方式：补充到「第三章·XX」末尾，作为新段落
   
2. 修订内容："[修订原文摘要]"
   → 融合方式：在「第二节·YY」的结论句之后，以 [修订] 标注插入

确认后开始整合，还是需要调整？
```

**第三步：执行整合**

用户确认（或直接说"帮我整理，不用问我"时跳过确认）后：

1. 用 Edit 工具将每条修订思考插入到规划好的位置
2. 插入时保持行文风格一致，融入自然，不要生硬地加"[修订]"标签——除非是明确的纠错（原文有误需标注）
3. **修订内容完整性原则**（最高优先级）：
   - **代码块原封不动**：修订章节中的代码块（\`\`\` 包裹的内容）必须原封不动地嵌入正文，不做任何改写、缩略或"总结"。代码不能做总结，丢失任何细节都可能导致功能异常
   - **正文不丢信息**：修订中的非代码文字，可以润色行文使其更自然，但必须保证所有信息点完整保留。禁止为了简洁而删减实质内容
   - **表格、列表等结构化内容**：同样需要完整保留原始结构和所有条目
4. 所有修订内容整合完毕后，**删除文章开头的整个修订章节**（它的使命已完成）
5. 如果文章有 `> **文档摘要**` 块，且整合的内容涉及新的核心要点，同步更新摘要块

**第四步：汇报**

```
✓ 已整合 3 条修订：
  - "关于 XX 的补充思考" → 插入到「第二节」末尾
  - "对 YY 结论的修正" → 在「第三节·ZZ」段落后插入修正说明  
  - "整体视角的补充" → 扩展到结论段
✓ 已删除开头的「修订」章节
✓ 已更新文档摘要块（新增核心要点：...）
```

## 目录同步执行流程

### 第一步：扫描目录

如果用户没有明确指定目录，询问目标目录路径。

使用 Glob 扫描目录下所有 `.md` 文件（排除 `README.md`），得到文件路径列表。

**增量模式下**：用 Bash 检查每个文件的修改时间，过滤出 mtime 距今 ≤ 7 天的文件：
```bash
find <目录> -name "*.md" ! -name "README.md" -newer $(date -v-7d +%Y%m%d 2>/dev/null || date -d '7 days ago' +%Y%m%d) -type f
```
或直接用 `stat` 逐文件判断。跳过 7 天内未修改的文件，并在简报中注明跳过数量。

**不要在主 agent 中读取文件内容。**

---

### 第二步：并发子 agent 分析每个文件

使用 Agent 工具**同时**为每个文件派发一个子 agent（在同一条消息中发出所有 Agent 调用）。

每个子 agent 的任务提示模板：

```
请读取文件：{文件路径}

分析后，返回一个 JSON 对象（不要输出其他内容）：

{
  "file": "文件名.md",
  "status": "new" | "stale" | "ok",
  "status_reason": "为什么是 stale 或 ok（new 时留空）",
  "summary_block": "完整的摘要块文本（仅 new/stale 时提供，ok 时为 null）",
  "summary_insert_before": "摘要块应插入在哪一行之前（该行的完整文本）",
  "heading_suggestions": [
    {
      "original": "原标题完整文本（含 ## 前缀）",
      "suggested": "建议标题完整文本（含 ## 前缀）",
      "reason": "原标题含义模糊或与内容不符的原因"
    }
  ],
  "has_revision": true | false,
  "revision_merges": [
    {
      "revision_text": "修订原文（完整内容）",
      "target_section": "目标章节标题或段落首句",
      "merge_type": "append" | "correction" | "new_section" | "expand_conclusion" | "cross_ref_only",
      "merged_text": "整合后应插入到目标位置的完整段落文本（cross_ref_only 时为需插入的交叉引用链接文本）"
    }
  ],
  "readme": {
    "title": "文档标题",
    "topics": "主题一句话描述",
    "use_cases": ["适合用本文完成的任务1", "适合用本文完成的任务2"],
    "not_for": ["不适合用本文解决的任务或边界，可为空数组"],
    "key_concepts": ["概念1", "概念2"],
    "key_takeaways": ["核心结论1：用一句话陈述该结论", "核心结论2"],
    "reading_stage": "入门" | "进阶" | "深入" | "实操",
    "relations": [
      {
        "type": "前置阅读" | "深入展开" | "实操示例" | "故障排查" | "相关概念" | "替代方案",
        "file": "yy.md",
        "reason": "为什么存在这个关系"
      }
    ],
    "agent_routing": {
      "when_to_open": ["用户意图或问题特征1", "用户意图或问题特征2"],
      "keywords": ["稳定检索词1", "稳定检索词2"]
    }
  }
}

判断规则：
- status=new：文件中不含 `> **文档摘要**`
- status=stale：有摘要块但满足以下任一条件：正文新增了重要章节或核心主题已变；摘要缺少"适合阅读场景"、"核心结论"或类型化关联等当前标准字段；**某章节占全文篇幅 > 40% 但摘要对其只有一行描述**（摘要描述的重量分布应与正文相称）
- status=ok：摘要与正文匹配，无实质差异

标题优化判断规则（heading_suggestions）：
- 只建议有实质问题的标题，不要为了改而改。触发条件：
  - 标题过于泛化（如"介绍"、"背景"、"概述"、"其他"、"说明"），无法区分与其他章节的差异
  - 标题与该章节实际内容明显不符
  - 同一文档中有多个标题用词重复，无法区分（如两个"使用方法"）
- 不触发条件：标题清晰具体、能准确反映内容（即使措辞简短），不建议修改
- 如果没有需要优化的标题，返回空数组 []

readme.key_takeaways 规则：
- 提取 1-3 条该文档最核心的结论或洞见，用完整句子陈述（不是章节名称，是观点/结论）
- 示例："工具调用失败率随并发数线性增长，超过 8 个并发时错误率超 30%"，而非"并发问题"

readme.use_cases / not_for 规则：
- `use_cases` 提取 1-3 个任务导向入口，使用"当你要……"或动宾短语表达，例如"配置一个新的 Feishu adapter"、"排查 token 刷新失败"
- `not_for` 只在边界清晰时填写，例如"不覆盖生产部署安全加固"；没有明确边界时返回空数组

readme.relations 规则：
- 必须使用固定 `type`，不要只返回散文描述
- `前置阅读` 表示理解本文前建议先读；`深入展开` 表示本文只概述、目标文档详细展开；`实操示例` 表示目标文档给出操作样例；`故障排查` 表示目标文档处理失败场景；`相关概念` 表示同主题互补；`替代方案` 表示不同路径或取舍
- `reason` 用一句话说明关系，不要超过 30 个汉字

readme.agent_routing 规则：
- `when_to_open` 写 Agent 在什么用户意图下应该打开本文，例如"用户询问配置字段含义"、"用户要定位连接失败原因"
- `keywords` 写稳定检索词，包含同义词、配置名、模块名或关键概念；不要堆砌泛词

修订章节识别规则：
- has_revision=true：文件开头（正文之前）存在标题含"修订"、"修订记录"、"后记补充"、"Revision"等字样的章节
- has_revision=false：不存在修订章节，revision_merges 返回空数组 []
- revision_merges 中每条记录描述一条修订思考应整合到正文的哪个位置及方式：
  - append：在目标章节/段落末尾追加为新段落
  - correction：在目标论断之后插入修正说明（行文自然融入，无需加特殊标签）
  - new_section：在最相关章节下新增子节
  - expand_conclusion：扩展引言或结论段
  - cross_ref_only：修订内容已在正文某章节展开，无需插入新内容，只需在原提及处补充指向该章节的交叉引用链接；`target_section` 填写原提及处的段落首句，`merged_text` 填写需插入的引用链接文本

修订内容完整性规则（merged_text 必须严格遵守）：
- **代码块原封不动**：修订中的代码块（\`\`\` 包裹的内容）必须原封不动地复制到 merged_text 中，不做任何改写、缩略或总结。代码不能做总结
- **正文不丢信息**：非代码文字可以润色行文使其更自然，但必须保证所有信息点完整保留。禁止为了简洁而删减实质内容
- **表格、列表等结构化内容**：同样需要完整保留原始结构和所有条目

摘要块格式（summary_block 必须严格遵守）：

> **文档摘要**
>
> [1-2 句话概括文档定位：这篇文档是什么、解决什么问题、适合什么阅读场景]
>
> **适合阅读场景：**
> - [当你需要完成/理解/排查的具体任务]
>
> **不适合解决：**
> - [明确边界；如没有边界则省略整个小节]
>
> **核心内容：**
> - [要点 1]
> - [要点 2]
>
> **核心结论：**
> - [完整观点或决策依据，不是章节名]
>
> **与其他文档的关联：**
> - [关系类型] [为什么关联] → `文件名.md`

摘要块写作规则：
- 摘要块的首段面向人类快速判断，列表字段面向人类扫描和 Agent 抽取
- "适合阅读场景"必须任务化，不写"适合所有读者"这类空泛描述
- "核心结论"必须能脱离全文单独成立
- "与其他文档的关联"必须以固定关系类型开头，例如 `[前置阅读]`、`[深入展开]`、`[实操示例]`、`[故障排查]`、`[相关概念]`、`[替代方案]`
- 对短文档可控制为每个小节 1-2 条，避免摘要比正文还重

```

收集所有子 agent 返回的 JSON。向用户简报扫描结果：
> 扫描到 8 篇文档：2 篇新增（无摘要）、1 篇已变更（摘要过时）、3 篇含修订章节待整合、2 篇有标题优化建议、2 篇无需更新。

如果所有文件均为 `ok` 且无修订章节、无标题建议，告知用户无需任何更新，结束执行。

**如有标题优化建议，在简报后展示并等待用户确认（与修订整合计划合并展示）：**

```
🏷️ 标题优化建议：

📄 aa.md
  - "## 介绍" → "## 为什么需要 XX：核心动机"（原标题过于泛化）
  - "## 其他" → "## 边界情况与注意事项"（原标题无法区分内容）

📄 bb.md
  - "## 使用方法" → "## 快速上手：三步配置流程"（与另一个"使用方法"章节重名）
```

**如有修订章节待整合，继续展示修订整合计划（格式同原有）。**

确认后一并执行，还是需要调整？

摘要块更新（无修订整合、无标题修改的文件）无需确认，可直接执行。

### 第三步：更新各文档的摘要块并整合修订

**摘要块写入**（status 为 `new` 或 `stale` 的文件）：

- `new` 类：将 `summary_block` 插入到 `summary_insert_before` 所指那一行之前（用 Edit 工具）
- `stale` 类：用 Edit 工具替换文件开头的整个旧摘要块

**标题优化**（有 heading_suggestions 的文件，与摘要块更新并行处理）：

用 Edit 工具将每条建议中的 `original` 替换为 `suggested`。标题优化不改变任何正文内容，只修改标题行本身。

**修订整合**（has_revision=true 的文件，与上述操作并行处理）：

按 `revision_merges` 中每条记录，用 Edit 工具将 `merged_text` 插入到 `target_section` 对应的位置。所有修订条目处理完毕后，删除文件开头的整个修订章节。若整合的内容涉及新的核心要点，同步更新摘要块。

**修订内容完整性原则**（最高优先级，适用于所有修订整合操作）：
- **代码块原封不动**：修订章节中的代码块（\`\`\` 包裹的内容）必须原封不动地嵌入正文，不做任何改写、缩略或"总结"。代码不能做总结，丢失任何细节都可能导致功能异常
- **正文不丢信息**：修订中的非代码文字，可以润色行文使其更自然，但必须保证所有信息点完整保留。禁止为了简洁而删减实质内容
- **表格、列表等结构化内容**：同样需要完整保留原始结构和所有条目

### 第四步：增量更新 README.md 索引

读取现有 README.md（如不存在则创建完整索引）。

对以下区域做**增量更新**，不重写整个文件：

1. **文档地图**（树形结构）：新文档按逻辑关系插入合适位置，而不是简单追加到末尾
2. **按任务查找**：维护"你想做什么 → 推荐阅读"表，这是人类和 Agent 的首要入口。格式：
   ```
   ## 按任务查找

   | 你想做什么 | 推荐阅读 | 说明 |
   |------------|----------|------|
   | 配置一个新 adapter | [adapter-guide.md](adapter-guide.md) | 覆盖字段含义和最小配置 |
   | 排查连接失败 | [troubleshooting.md](troubleshooting.md) | 按错误现象定位原因 |
   ```
3. **各文档简介表**：每篇文档一行，包含文件链接、主题、适合场景、关键概念、**核心结论**（来自 `key_takeaways`，1-2 条）；新文档添加行，已更新摘要的文档同步更新
4. **Agent 快速路由**（新区域，如不存在则创建）：维护"用户意图/关键词 → 候选文档"的轻量索引，帮助 Agent 在不阅读全文时选上下文。格式：
   ```
   ## Agent 快速路由

   | 用户意图或关键词 | 优先打开 | 备注 |
   |------------------|----------|------|
   | token、鉴权失败、401 | [auth.md](auth.md) | 先看错误码映射 |
   | adapter 配置字段 | [config.md](config.md) | 覆盖字段默认值和边界 |
   ```
5. **交叉引用区域**：使用固定关系类型维护文档关系；新文档引入新的概念关系时，在对应小节补充；已更新摘要的文档若涉及关系变化，同步调整。推荐小节：
   - `### 前置阅读`
   - `### 深入展开`
   - `### 实操示例`
   - `### 故障排查`
   - `### 相关概念`
   - `### 替代方案`
6. **推荐阅读顺序**：新文档判断应插入哪个阅读阶段（入门/进阶/深入/实操）
7. **概念索引**（新区域，如不存在则创建）：维护一张"概念 → 文章"的反向映射表。格式：
   ```
   ## 概念索引
   
   | 概念 | 相关文档 |
   |------|----------|
   | XX 概念 | [aa.md](aa.md)、[bb.md](bb.md) |
   | YY 模式 | [cc.md](cc.md) |
   ```
   新文档的 `key_concepts` 中每个概念，检查是否已在索引中，若无则新增行，若有则补充该文档链接。

**重要原则：**
- 只更新需要变更的部分，用 Edit 工具精确替换，保留用户对 README.md 的其他自定义内容
- 如果 README.md 不存在或结构差异过大，才进行整体重建
- README 的首屏应优先呈现"文档地图"和"按任务查找"，不要让读者先读维护说明或长篇背景
- 表格字段保持短句，避免把整段摘要塞进单元格；长解释应留在文档摘要块或正文中

## 注意事项

- **不要过度更新**：如果摘要基本准确，只是措辞与正文有轻微差异，不需要更新。只有实质性内容变化（新增章节、主题转变、关键结论改变）才触发更新
- **修订内容不得丢失信息**：整合修订时，代码块必须原封不动嵌入，正文可以润色但不能删减信息点。这是最高优先级规则
- **并行读取**：扫描阶段可以并发读取多个文件，提高效率
- **不要创建不必要的文件**：除摘要块和 README.md 之外，不新建任何文件
- **顺手检查结构性问题**：整理修订时，如发现以下情况可主动提示用户（征得同意后修复）：
  - **内容重复**：同一主题在文章两处出现（浅描述 + 深章节并存），浅处应改为指向深处的引用
  - **缩进层级与逻辑不符**：bullet 的从属关系应基于逻辑，不能只因"挨着"就缩进在某条目下
  - **子章节拆分机会**：顶级 bullet ≥ 3 个且各主题独立、各有子内容时，升级为 `###` 子节可读性更好
